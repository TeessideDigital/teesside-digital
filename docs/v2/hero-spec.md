## 15. Accessibility requirements

Target WCAG 2.2 AA. These are requirements, not conformance claims.

- Preserve one page H1, useful landmarks, logical source order and a working skip route past repeated navigation.
- Keep all links, the enquiry action and theme utility keyboard accessible with visible, unobscured focus.
- Use meaningful current-location and theme-selected states without relying on colour, icon or movement alone.
- Keep activation targets stable when inner visual elements move. Avoid layout shift and focus-ring clipping.
- Test text, states, necessary boundaries and de-emphasis in both themes. A dark-theme pass does not prove light-theme contrast.
- Preserve content at zoom, text enlargement and spacing overrides, including short viewport access to the full index.
- Ensure touch needs no hover, and reduced motion retains full function and understanding.
- Keep the logo/Home accessible name concise without repeated image/text announcements.
- Do not hide the offer, descriptors or limitations in animated clips, canvas, images or hover-only states.
- Verify text contrast with the eventual image, every relevant crop and both themes, including image failure.
- Determine image semantics from its actual use: use empty alternative text if purely decorative; if it conveys meaningful place/context, provide concise accurate alternative text. Do not turn it into an unsupported project claim.

Later validation must also consider browser/user accessibility overrides. Defaulting to Dark does not justify suppressing forced-colour behaviour or other necessary user adaptations. Any conflict between a visual treatment and usable access requires revising the treatment.

## 16. Performance requirements

Retain Astro, TypeScript and the static-first foundation. Essential offer content, links and enquiry access must not require a client runtime. This is not a zero-JavaScript prohibition on the approved theme utility or justified kinetic enhancement.

Theme initialisation and persistence must justify their cost and avoid an obvious wrong-theme flash. Exact mechanics and implementation budget remain deferred. No framework, animation library or React island is required merely by this specification.

The substantial hero image introduces a possible LCP and transfer/decode cost. Later implementation must choose an appropriately sized, optimised responsive asset, reserve its layout dimensions and make loading/priority decisions for its actual first-view role. Avoid downloading an unnecessarily large desktop crop on a phone or delaying essential content for image decoding. Exact asset and loading mechanics remain deferred.

Font transfer/fallback shifts, animated clipping/scale costs and later project imagery also require measurement. The static fallback must remain useful; a readable no-image state does not remove the requirement to meet performance targets with the selected image present.

Project targets remain LCP <2.5s, CLS <0.1, INP <200ms, and Lighthouse Performance >=90, Accessibility >=95, Best Practices >=95, SEO >=95. These are targets, not achieved scores. Test real implemented pages and record environment and limitations later.

Do not add decorative video, WebGL or a gallery framework to make the dark identity feel complete. Prefer the least costly technique that achieves a justified interaction and retains a robust static equivalent.
