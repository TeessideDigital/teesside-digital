# Teesside Digital V2 - Phase 0 Approved Decisions

**Status:** Approved strategic decisions following review of `docs/v2/phase-0-audit.md`

**Purpose:** This document records Dave's approved decisions after reviewing the Phase 0 audit. Where this document differs from recommendations in the audit, this document takes precedence.

## 1. Target Market

Teesside Digital will initially target **small and owner-led businesses across Teesside**, regardless of sector.

The launch strategy is geographically focused rather than industry-specific.

Priority:
1. Teesside
2. Wider North East
3. UK-wide where appropriate

Do not position Teesside Digital as a business only for trades, construction firms, joinery companies or any other single sector.

The early objective is to win realistic, manageable projects Dave can personally deliver to a high standard and use to build genuine client experience, testimonials, case studies, reputation and stronger commercial proof.

Do not begin by chasing enterprise-scale or very high-value engagements that exceed current evidence, capacity or operating model.

## 2. Service Structure

The V2 service structure will be:

1. **Websites & Web Development**
2. **Apps & Digital Tools**
3. **Automation & AI**

Across all three, **security, accessibility and performance** are core engineering standards rather than separate marketing add-ons.

### Websites & Web Development
Potential scope includes business websites, ecommerce where appropriate, landing pages, custom frontend development, responsive design, accessibility, SEO-aware implementation, integrations and security-conscious development.

### Apps & Digital Tools
Potential scope includes web applications, customer portals, booking systems, quotation tools, dashboards, internal tools, business systems, PWAs and mobile applications where a genuine use case justifies them.

Do not recommend a native mobile app simply because the client asks for one. Choose the architecture that best solves the business problem.

### Automation & AI
Potential scope includes workflow automation, enquiry routing, quotation workflows, repetitive administration, document processing, system integrations, AI-assisted internal tools and carefully designed LLM workflows.

Do not force AI into a solution where deterministic automation is more appropriate.

## 3. Cybersecurity Boundaries

Cybersecurity will no longer be presented as an equally broad standalone consultancy pillar.

Security will primarily be communicated as part of Teesside Digital's engineering standard across websites, apps and automation.

Publicly defensible standalone security work may include secure web development, website security reviews, application security checks, configuration review, security hardening, secure coding practices, dependency/security hygiene and remediation guidance.

Do not currently advertise broad specialist services such as penetration testing, incident response, breach recovery, formal compliance consultancy, ISO assurance, enterprise infrastructure security design or continuous security monitoring.

These may only be added later if capability, process, evidence and operating arrangements support the claims.

Dave's previous cybersecurity study supports a security-conscious engineering approach but must not be presented as professional security certification.

## 4. Demo Projects and Portfolio Proof

### North East Joinery
Keep.

Current state:
- the website is built
- it requires substantial additional work before it should be presented as a polished showcase

Until then, describe it honestly as an active demonstration project or work in progress.

It must not be presented as a completed client project, measured commercial success or finished studio-quality case study.

Once improved, it should become strong evidence for Websites & Web Development using real screenshots, live demo links, source repository links where appropriate, design/engineering decisions, responsive implementation, accessibility/performance evidence and clear demo disclosure.

### QuoteFlow
Keep as a project, but do not currently use as finished public proof.

Current state:

It should remain off the main portfolio until there is enough real functionality to inspect.

Once built properly, QuoteFlow should become evidence for Apps & Digital Tools.

### SiteGuard
Remove from current public proof.

Do not delete the idea permanently. It may return later if a real working product is built and can truthfully demonstrate capability.

### Portfolio principle
**Quality over quantity.**

Longer-term proof structure:
- Teesside Digital V2 -> own-site design and engineering proof
- North East Joinery -> website/web-development proof
- QuoteFlow -> app/digital-tool proof
- future project -> Automation & AI proof

## 5. Website Health Check

Remove the current automated Website Health Check and its percentage-scoring model from V2.

Remove automated overall/security/accessibility/performance scores, "Excellent / Good / Poor" style assurance, sales-based deductions and unreliable automated report-delivery claims.

Replace it with a **manual website review request**.

Proposed flow:
1. Visitor submits name, email, website URL and optional context.
2. Dave receives the request.
3. Dave manually reviews the website.
4. Dave completes a structured report.
5. Dave emails the report back personally.

The review may cover first impression/trust, clarity of offer, mobile experience, CTAs/enquiry flow, performance, obvious accessibility issues, obvious technical/security hygiene issues, priority improvements and whether Teesside Digital could help.

The review should be genuinely useful even if the recipient never becomes a customer.

Do not promise a fixed turnaround until realistic capacity is established.

V2 may later include an interactive technical demonstration, but it must not pretend to perform a complete audit of arbitrary external websites.

## 6. Primary Conversion Strategy

The primary conversion objective is a **qualified project enquiry sent directly to Dave**.

The manual website review is the secondary conversion path.

Primary CTA direction: **Discuss your project**. Exact final copy will be decided in the content phase.

The enquiry form should focus on understanding the problem rather than forcing the visitor to diagnose the technical solution.

Likely fields:
- name
- email
- business name
- what they need help with
- optional website URL
- optional budget range
- optional preferred contact method

Avoid a large technical service selector unless it proves genuinely useful.

Secondary CTA: **Request a website review**.

Avoid misleading/vague CTAs such as Get Started, Schedule Consultation when no scheduling system exists, urgent-call messaging without a real phone route, forcing every visitor through a free automated scan, and generic Learn More where a more specific action exists.

## 7. Creative Ambition

Teesside Digital V2 should target **Level 2 - distinctive studio quality**.

It should be high-end, original, memorable, visually confident, sophisticated, typographically strong, interaction-aware and carefully composed, but not theatrical for its own sake.

V2 may use strong typography, editorial composition, asymmetry, controlled depth, deliberate motion, sophisticated interactions, memorable hero treatment, carefully designed responsive behaviour and one or two signature visual moments.

Avoid by default: WebGL merely to look expensive, excessive scroll choreography, scroll-jacking, constant parallax, 3D chrome objects, animation on every element, giant meaningless typography and heavy effects that damage performance/usability.

Clarity, credibility, accessibility and speed remain higher priorities than spectacle.

## 8. Visual Independence from North East Joinery

Teesside Digital V2 must be visually and structurally independent from North East Joinery.

It must not simply be a recoloured or more polished version of the joinery site.

The two brands should differ meaningfully in typography, grid system, spacing rhythm, hero structure, navigation, CTA arrangement, section composition, content density, card usage, surface treatment, imagery, motion language, interaction patterns and overall spatial language.

North East Joinery may remain warmer, more tactile, image/material-led, conventional and craft/business focused.

Teesside Digital should become more editorial, engineered, asymmetric, conceptual, typographically distinctive, interaction-led and less dependent on the standard hero/cards/section-stack pattern.

The two sites should feel like they were designed for completely different brands by the same capable designer, not generated from one house template.

## 9. Founder Positioning

**Teesside Digital leads as the brand. Dave provides differentiation and trust.**

The website should not become a personal portfolio or biography-first experience.

The visitor should first understand what Teesside Digital does, whether it is relevant, what evidence exists and who is responsible for the work.

Homepage founder content should focus on direct access to Dave, personal accountability, practical business experience, creative craftsmanship, technical education and local Teesside connection.

The About page should tell the full chronology honestly.

Use `I` where Dave is personally speaking/responsible, `Teesside Digital` for company-level statements, and `we` only where genuinely appropriate.

Do not manufacture a large-agency persona.

## 11. Pricing

Remove:
- the existing GBP 5k-50k+ public range
- anti-agency price attacks
- claims that agencies charge more merely because of overhead

Do not invent replacement prices during the redesign.

Pricing should be established from real delivery economics: estimated effort, target effective rate, software/hosting costs, risk, contingency, support commitment, margin, customer value and project complexity.

Later, Teesside Digital may publish starting prices, indicative bands or minimum engagement levels if those improve customer qualification.

Do not position Teesside Digital as "cheap because solo".

The commercial advantages of the solo model are direct communication, accountability, continuity and lower organisational overhead.

## 12. Capacity, Support and Solo Delivery

Use the solo model as a direct-accountability advantage while maintaining realistic boundaries.

Do not advertise 24/7 support, emergency response, unlimited support, same-day response guarantees unless genuinely sustainable, or formal SLAs that are not operationally supported.

Projects should be taken on at a level where Dave can remain personally involved from first conversation through delivery.

Do not heavily foreground university scheduling or imply unreliability.

Future post-launch model should distinguish:
1. launch
2. defined defect/correction period
3. optional ongoing support/maintenance
4. new development quoted separately

Exact warranty/support periods should be established later based on actual capacity.

## 13. Public Claims, Legal Content and Credibility

Only publish claims that can be evidenced.

Do not publish unsupported assertions such as fully accessible, no vulnerabilities, guaranteed security, tested with specific assistive technology unless actually tested, quarterly audits unless actually performed, specific retention practices unless implemented, processor/infrastructure locations unless verified, or certifications/qualifications that do not exist.

A defensible accessibility direction is:

**Built with WCAG 2.2 AA as the target, with testing and ongoing improvement.**

Do not claim complete conformance without appropriate evidence.

Rebuild privacy, accessibility and service/legal content from actual operating facts.

Do not rely on generic boilerplate describing practices Teesside Digital does not actually follow.

## 14. Technical Baseline

Keep:
- Astro
- TypeScript
- Netlify
- static-first architecture
- structured project/service data
- reusable component architecture
- sitemap/canonical infrastructure
- simple deployment model

Do not migrate frameworks merely because V2 is a redesign.

During implementation review/correct:
- lockfile policy and reproducible installs
- Astro diagnostics/type checking
- dependency advisories
- outdated dependencies where appropriate
- stale configuration
- unused feature flags
- image optimisation
- raw multi-megabyte assets
- responsive issues
- metadata/schema inconsistencies
- security headers
- CSP feasibility
- unnecessary hydration
- JavaScript cost

Do not run destructive automated dependency upgrades blindly.

## 15. Evidence and Measurement Standard

Any measurable public claim must be traceable to real evidence.

Where relevant, record:
- what was measured
- date
- environment
- method/tool
- actual result
- relevant limitations

This applies to performance, Lighthouse, accessibility, Core Web Vitals, security, before/after improvements, conversion results, client outcomes, time saved and automation benefits.

Do not publish projected outcomes as measured outcomes, invented statistics, unrepeatable performance claims or Health Check scores as evidence of genuine quality.
